# 本地筛图实验：进展、取舍和复现

## 目标与现状

目标是用户需要提醒时，从画面条件出现到有效声音不超过3秒。希望云端建立合同并在命中时整理播报，本地承担频繁筛图，降低反复云请求造成的尾延迟和支出。并非完全离线语音助手。

设备为iPhone 17 Pro；35B模型文件约16.62GB，1B约1.78GB。磁盘空间和运行内存是两回事；实际进程预算约6GiB，GPU已参与运算。权重不在仓库，目录和精确文件校验见模型catalog。云端账户和手机签名各自配置。

| 方案 | 已跑通的分工 | 真实限制 |
| --- | --- | --- |
| 35B-A3B | 阿里建立合同；本地Y/N；命中后阿里结合当前图整理与发声 | 用户反馈较准；本地仍约4—8秒，未达总延迟目标 |
| 1B + Lite审核 + 原Live（当前） | Google Live合同；本地Y/N；正触发才由手机直连Lite审核；应用解析后交原Live播报 | 1B放行偏多时仍会频繁请求Lite；减压和费用下降未作保证 |
| 1B + Live直接复核（历史） | 本地Y/N触发当前直连Live看图并决定是否说；当前不再加载此路径 | 本地约0.4—0.55秒；曾有成功交付，也出现12秒等待超时和只有文字无音频 |
| 1B完整独立筛图 | 曾让本地输出完整结构，再由应用决定开口 | 实测误报和漏报并存，已移除；不作为可用方案宣传 |

35B没有重新训练、删专家、减少top-8或跳过权重。本地缓存保存不可变专家字节，不缓存图片答案；未缓存专家仍按原路由读取。1B的Y不能当现场事实，当前由Lite依据同一图与完整合同审核，沿既有四类状态、实例和音频交付规则运行；这不是完全本地视觉判断。1B为N时不请求云模型，但如果1B始终放行，Lite仍可能接近每轮被调用。Live保持原慧眼问答、合同和播报职责，不叠加提醒复核，不添加新Live会话或额外云模型。旧Live直接复核源码保留用于研究，不作为当前入口。

## 35B实测

固定官方应用源`fa9d837`、引擎`96bbf61`；精确提交在provenance与构建脚本。保留256批宽，用每层最多32个只读专家权重缓存，替换原decode窗口的内存用途；普通入口默认开启。8路读取不变。

同一图、同一合同，每组3次，单位毫秒：

| 方案 | 首次含合同准备 | 第二次 | 第三次 |
| --- | ---: | ---: | ---: |
| 原方案8路 | 8924.177 | 5615.022 | 5562.410 |
| 新缓存8路 | 7511.415 | 4583.236 | 4500.780 |
| 新缓存1路 | 9955.353 | 5670.793 | 5543.792 |
| 新缓存4路 | 7808.360 | 4574.020 | 4452.657 |

主对照后两次中位5588.716→4542.008ms，快约18.7%。权重读取请求6401→4802MiB，读取等待约3773→2836ms。空闲后的进程占用约2.45→3.58GB，是以内存换读取。12次输出均Y、温度状态0、视觉常驻；固定顺序且未随机交换，不是动态准确率验收。

随后真实使用完成9次35B筛图，中位4544.504ms；同合同复用帧3876.810—4692.432ms，新合同首帧6299.547—7652.678ms。9次均视觉常驻，无内存警告或取消，三份一次性任务完成音频交付。**这些是本地筛图时间，不包含等待条件出现、阿里整理和声音播放，不能称为3秒方案。**

## 已试过但不应重复误判的优化

- 固定系统规则和合同KV/SSM复用有效，避免每帧重新准备合同。
- 视觉塔GPU常驻、去掉逐帧静态预热有效；内存警告仍可安全取消并释放。
- 8改16路读取没有明确收益。新缓存4路比8路只快约29ms，证据不足，不换默认；1路更慢。
- 每4个token计算、56槽缓存失败：本地10.75—13.01秒，并有5次内存警告和取消，已经撤回。
- 单Y/N采样后跳过反馈的快返只做过专项检查，没有手机提速证据，未启用。
- 官方连续解码token/s不能替代此场景单图prefill/首判时间；默认不启用DSpark。

## 如何复现

先按[构建说明](ios-build.md)准备自己的iPhone、模型和应用。普通入口为阿里页“本地主动提醒（阿里声音）”，35B缓存默认开；1B入口为谷歌直连声音。两者不能同时加载。

离线对照使用`LocalScreenBenchmarkView`，无摄像头、麦克风、云请求或提醒提交。通过Xcode或自己的USB工具，把有权使用的`frame.jpg`与`fixture.json`放到应用Documents的`LocalScreenBenchmark`目录：

```json
{"prompt":"主体：测试目标\n核验条件：当前图中清晰出现测试目标","samples":3,"model":"35b"}
```

启动参数`-huiyanLocalScreenBenchmark`运行原基线；再加`-huiyan35bPrefillReadCache`运行新缓存。同图同合同、不重写输入，分别读取目录中`result-io8.json`与`result-io8-readcache.json`。`model`设`1b`可测1B。正常入口不读取离线素材。精确计时、内存计划、温度状态、输入哈希由程序记录；不要只比较首帧或最快帧。

希望协助：单图prefill专家读盘与GPU计算的流水并行、更合适的跨帧缓存、可行的量化/架构优化，以及在准确率不退步时减少必须触达的云端次数。先提供对照结果，再改默认路径。
